## 背诵总纲（30 秒电梯版）

**这是全篇的浓缩，进面试间先稳住这一段：**

> 我做的项目是一个企业知识库问答系统。背景是公司/团队内部文档散落在 Word、PDF、飞书/语雀里，员工查制度、查流程要翻半天，而且很多问题大模型直接答会"一本正经地胡说八道"。我的方案是 **RAG，检索增强生成**——把文档切块后做向量化，用户提问时先从知识库里检索最相关的段落，再连同问题一起交给大模型回答，保证答案有据可依。我负责了从文档解析、切片、向量入库到检索、Prompt 编排、前后端的完整链路。上线后把**答案准确率从直接问大模型的【X】% 提升到【Y】%**，并且每条回答都能给出引用出处，方便用户核对。

（约 30 秒，可背）

## 第一段：项目背景与为什么不用微调（约 40 秒）

**面试官会先问"你做了什么项目"，这不能只报菜名，要讲清动机：**

> 这个项目的出发点是一个真实痛点：我们团队的知识分散在【N】个文档里，比如员工手册、FAQ、项目规范，每天都有同事在群里问同样的问题。最开始我试过两种方案：
>
> 第一种，直接把几万字文档全塞给大模型——**不现实**，一是上下文窗口有限，塞不下，二是塞下了成本也扛不住，一次问答要烧大量 token，三是文档更新后模型不会跟着变。
>
> 第二种，拿去微调模型——**更不划算**，知识库每周都在更新，每次更新都重新微调，周期长、成本高，而且微调容易让模型学到"死知识"，还可能导致它原有的通用能力退化，也就是"灾难性遗忘"。
>
> 所以最终选了 **RAG**。它把"记忆"从模型参数里拿出来，放到外部数据库里。知识更新只需要重新灌文档，模型本身不用动，**成本低、时效性好、可解释性强**——答案能追溯到原始文档，这对企业内部场景特别重要。

**要点提示：**
- 背熟"塞不进 / 太贵 / 会过时"三个不选直接塞的理由
- 背熟"微调贵 / 更新慢 / 会遗忘"三个不选微调的理由
- 收尾落在"可解释性"，这是企业最看重的

## 第二段：技术栈与整体架构（约 40 秒）

**讲架构要配合画图，边说边画：**

> 技术栈方面，后端用的 **Node.js + Express / 或 Spring Boot**，因为我对它最熟；向量库选的 **pgvector**（或 Milvus/Qdrant），挂在 PostgreSQL 上，**不用额外维护一套独立数据库**；Embedding 用的是 **bge 系列模型**（或 text-embedding 系列），大模型用的是 **DeepSeek / GLM / 通义千问**；前端是 Vue。
>
> 整体分四层：
> 第一层是**文档接入层**，支持上传 Word、PDF、Markdown，用对应的解析库把文字抽出来；
> 第二层是**离线索引层**，负责切片、向量化、写入向量库，这一层用任务队列做成异步的，避免大文档卡住接口；
> 第三层是**在线问答层**，用户提问 → 向量检索召回 top-K → 拼装 Prompt → 大模型流式生成；
> 第四层是**展示层**，知识库管理后台 + 问答页面，答案下方会列出引用的原文片段，高亮命中部分。

**要点提示：**
- 边说边在纸上画四层框图，面试官很吃这套
- "为什么选 pgvector 不选独立向量库"是你展示思考的点：**少一套运维、事务能力强**；数据量大再迁 Milvus
- 一定强调"离线索引异步化"，体现工程思维

## 第三段：核心流程走一遍（约 60 秒，重点背）

**这段是 RAG 的主流程，几乎必问，背到能闭眼默写：**

> 我详细讲一下一条问答的完整链路，分成离线、在线两部分。
>
> **离线阶段（文档入库）：**
> 1. 文档上传后进消息队列，worker 拉取任务；
> 2. 先做解析，PDF/Word 转成纯文本，遇到表格我会转成 Markdown 表格，保留结构；
> 3. **切片**是最关键的一步。我先按章节标题定位，再按【500~800 字】的窗口切，相邻块之间留【50~100 字】重叠，避免一句话被从中间切断。对结构化很强的文档，我会走"父子块"策略，父块管语义、子块管精度；
> 4. 每个块调 Embedding 模型转成 1024 维向量，连同原文、标题、文件 ID、上传时间一起写入向量库，并建好 HNSW 索引。
>
> **在线阶段（用户提问）：**
> 1. 用户提问后，先用同样的 Embedding 模型把问题向量化；
> 2. 到向量库做相似度检索，取回 top-K，K 我设的是【5】；
> 3. 为了让结果更准，我还加了**混合检索**——关键词用 BM25 同步召回，两路结果做分数融合；
> 4. 召回的段落按相关度排序，拼成 Prompt 的上下文，再交给大模型；
> 5. 大模型只允许**基于给定的上下文回答**，如果上下文里没有答案，必须明确说"知识库中没有相关内容"，不许瞎编；
> 6. 答案通过 SSE 流式返回前端，同时把引用片段一起返回，前端高亮展示。

**要点提示：**
- 这段必须脱稿背，是"保命题"
- 数字（切片大小、重叠、K 值）先背占位，做完项目填真实值
- 结尾"模型不许瞎编 + 给出引用"是亮点，多强调

## 第四段：检索不准的优化之路（约 60 秒，最能拉开差距的一段）

**面试官最想听"你踩过什么坑、怎么优化"，这是区分培训班和真实做过的人的关键：**

> 做的时候踩的坑不少，我讲三个印象最深的：
>
> **坑一：切片策略导致召回不准。** 一开始我固定按 500 字切，结果把文档里的表格、条款从中间切断了，检索时语义不完整。我改成**先按标题层级切，再对超长块二次切**，表格单独处理，召回质量明显改善，命中率从【X】% 提到【Y】%。
>
> **坑二：用户问法和文档写法对不上。** 比如文档里写"年假规则"，用户问的是"我能休几天假"，纯向量检索容易漏。我加了两层优化：第一层是**查询改写**，让大模型先对用户问题做一次扩展，补全同义词和完整表述；第二层是**混合检索**，BM25 管关键词精确匹配，向量管语义相近，两路融合排序。融合后 top-5 的准确率从【X】% 提到【Y】%。
>
> **坑三：长文档被淹没。** 文档特别长、相关段落分散时，top-K 容易召回一堆次相关内容。我引入 **Re-rank 重排**——粗召回 20 条，再用更精细的模型/规则重新排序，只留 top-5 进上下文。重排后答案引用的命中率从【X】% 提到【Y】%。

**要点提示：**
- 每讲一个坑，必须带"前→后"的数字对比，没有数字等于没优化
- 三个坑的顺序可以按你实际经历换，但结构保持：问题 → 方案 → 量化结果
- 结尾可补一句方法论："我后来建了一个 20~30 条的评测集，每次改动先在评测集上跑，不靠感觉调参"——这句是点睛之笔

## 第五段：如何保证答案质量与评测（约 40 秒）

> 为了保证不是"感觉变好了"，我建了一套**轻量评测**：从真实问答里攒了【30】条测试题，每道题标注了标准答案和它对应的原文段落。
>
> 我关注三个指标：
> 第一是**召回命中率**——标准答案的段落有没有出现在召回的 top-5 里；
> 第二是**忠实度**——大模型生成的内容有没有超出给定上下文，有没有幻觉；
> 第三是**答案正确率**——我人工判断生成答案能不能解决用户问题。
>
> 每次改切片策略、换 Embedding、调 K 值，都在这套集子上回归一遍。用这套方法，最终把召回命中率稳定在【X】% 以上，人工抽测答案正确率【Y】%。

**要点提示：**
- "先有评测，再谈优化"是你和专业选手的最大区别，务必背出三个指标名
- 指标数字做完项目填真实的，哪怕粗糙也比没有强

## 附 1：高频追问 & 标准应答（背熟，考你接得住）

**Q1：为什么选 RAG 不选微调？**
> 我的判断依据是三点：更新频率、成本、可解释性。知识库每周更新，RAG 重灌文档即可，微调要重新训练；微调一次成本高、周期长；最关键是企业场景要求答案能溯源，RAG 天然带引用，微调做不到。只有当知识相对固定、表达格式要求高度统一（比如让模型固定输出某种 JSON 报表）时，我才会考虑微调。

**Q2：Embedding 模型怎么选的？**
> 我对比了【bge-large / text-embedding 系列】在中文场景的表现，用我们自己的文档集跑了一版检索命中率，bge 对我们这种中文业务文档效果更好，就选了它。选型不是看榜单，是拿自己的数据说话。

**Q3：向量检索和关键词检索各自的优缺点？**
> 向量检索懂语义，"年假能休几天"能匹配到"年假规则"，但容易在专有名词、精确编号上失手，比如查"HR-2024-03 号文"；关键词检索正好反过来，精确匹配强但不懂同义表达。所以我把两者做混合，扬长避短。

**Q4：K 值设多大？为什么？**
> K 我设的 5。太小容易漏关键内容，太大会把不相关的噪音塞进上下文，既浪费 token 又干扰模型。我是用评测集测出来的，K=5 时命中率和忠实度综合最好。

**Q5：上下文拼太多会不会超过窗口？**
> 会，所以我对单条上下文有长度上限，超长就截断；同时 Prompt 里会按相关度排序，把最相关的放前面，因为模型对位置靠后的内容注意力会衰减。

**Q6：知识库更新了，旧内容怎么办？**
> 我做了版本管理：文档重新上传会生成新版本，删除旧切片写入新切片，按文件 ID + 版本号区分；检索时只查最新版本，并且支持按时间过滤，比如"只看今年发的制度"。

**Q7：文档里是图片/扫描件怎么办？**
> 我接了 OCR 做预处理，扫描件先识别成文字再走后面的链路；如果面试官追问，可以补一句"更复杂的图表我会用多模态模型先做描述抽取"。

**Q8：怎么防止模型胡编？**
> 三道防线：第一，Prompt 强约束"只基于上下文回答，没有就说不知道"；第二，后处理校验，如果答案里出现来源中没有的关键实体，打回重写或降低置信度提示；第三，给每条答案附引用，用户能自己核对——**让用户来监督模型**。

**Q9：成本怎么算的？**
> 一次问答的成本 = 检索阶段 embedding 费用（很低）+ 生成阶段按输入输出 token 计费。我实测单次问答大概【X 元】，主要开销在召回的上下文上，所以我通过控 K 值、控单条长度来压成本，另外热点问题我做了结果缓存。

**Q10：如果加"多租户知识隔离"怎么设计？**
> 每个租户一个知识库命名空间，切片入库时打上租户 ID 标签，检索时在元数据过滤层强制拼上租户条件，保证 A 租户永远检不到 B 租户的数据；权限再细分到文档级，由后端的权限服务统一控制。
